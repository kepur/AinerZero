## 授权能否被绕过

替身副本里，`generate_sequence` 装了计数钩子，下表的「生成」是实际生成的世界数（`bypass_r2c.json`）。

| 情形 | 判定 | 生成 |
|---|---|---|
| 日志在运行目录外，无标记 | 拒绝 | 0 |
| 在 `final-final/` 里，无标记 | 拒绝 | 0 |
| `final-final/worlds.jsonl` 是指向外面的符号链接，有标记 | 拒绝 | 0 |
| `final-final` 目录本身是指向外面的符号链接，有标记 | 拒绝 | 0 |
| 目录名换大小写（`FINAL-FINAL`，大小写不敏感的文件系统），有标记 | 拒绝 | 0 |
| 标记是个目录 | 拒绝 | 0 |
| final 型名字套 dev 规则 | 拒绝 | 0 |
| 用 `..` 绕一圈到运行文件，有标记 | 放行 | 1 |
| 外面的符号链接指向运行文件，有标记 | 放行 | 1 |
| 伪造标记和 `final-final/worlds.jsonl` | 放行 | 1 |
| 任意 `dev-*/worlds.jsonl` 加空账本 `[]` | 放行 | 1 |

- **前 7 种全部守住，拒绝都发生在生成之前。**
- **第 8、9 种无害：** 路径最终都落在这次运行自己的文件上，只有在标记已存在、也就是 final 已经读过以后才会放行。
- **第 10 种是蓄意伪造，在真仓库里会自曝：** 冻结的 `consume_final_read` 遇到已存在的标记会拒绝（「final has already been read」），运行器遇到已存在的运行目录也会拒绝。所以伪造标记等于毁掉真正的 final，不可能悄悄发生。至于有人另写代码、直接以 `allow_registered=True` 调用生成器，这不在这道守卫的防范范围内，它防的是误用。
- **第 11 种只差一点：** dev 授权只看账本文件存不存在，不核对里面有没有这一次的 use-id。好在本阶段 dev 上限是 0，永远不会有合法的 dev 运行，所以不影响任何结论（建议 1）。
